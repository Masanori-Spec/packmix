# 面接・説明のための確認メモ

この文章は本人の経験を代筆したものではない。AI支援で作られたコードを読み、説明・変更・再検証した後に、本人が行った範囲だけを説明する。

## 1分で説明する構成

1. 対象：少人数のイベントで備品を準備する人
2. 問題：入数の違うパックを組み合わせると、最安と余り最少が一致しない
3. 実装：人数・在庫を含む厳密な整数最適化と、人数変更の区切りを表示
4. 検証：独立した全探索との1,000ケース比較。性能の対象範囲を明記
5. 未検証：実需要、ブラウザ実機、アクセシビリティ、低速端末

## 説明できるべき設計判断

- なぜ単価順の貪欲法では十分でないのか。32枚の例以外で反例を作れるか
- なぜ探索上限を有限にできるのか。無料のパックや割引があると何が変わるか
- 同点時の条件はどの順か。なぜ必要か
- オラクルが本体と同じバグを持つ危険をどう減らしたか
- 人数の区間で一定なのは何か。余りまで一定でない理由は何か
- 品目ごとの最適化を合算してよい条件は何か
- Numberで安全な最大値はどこか。32bit整数に金額を入れると何が壊れるか
- JSONからのインポートで、深さ・サイズ・prototype pollution・DOM XSSをどう扱ったか
- DOM負荷とコア計算時間を分けて測る理由は何か

## 自分で試す小さな改修

未実施の練習課題。実施した場合だけ経験として話す。

1. 品目ごとに方針を選ぶ機能を追加し、保存スキーマをversion 2へ移行する
2. 無制限購入の代わりにパックごとの上限を付け、有限個ナップサックへ変更する
3. 区間表をキーボードのみで操作して改善点を記録する
4. 極端に長い備品名・500億円表示を小画面で確認する

## 需要を調べるなら

実在する利用者への連絡はまだ行っていない。許可を得た後で、イベント準備の経験者に次を観察する。

- 直近の備品購入で何をどう計算したか。具体的な手順とやり直し回数
- 価格と余りを比較する価値があるか、どちらを優先するか
- 人数変更の境目を知って決定が変わるか
- 入数・価格の手入力が面倒か。送料・店舗差のほうが重要か

成功指標候補は作業時間、計算ミス、購入判断の変化、再利用意思。定量的な実績はまだない。
