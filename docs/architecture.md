# 設計メモ

## 責務

- `src/optimizer.mjs`: データ検証、JSONパース、厳密な最適化、集計、人数区間。DOMや外部I/Oに依存しない
- `src/draft.mjs`: 未検証の編集中データから、指定IDの行だけを除く。残る編集値は検証の成否によらず保持
- `src/app.mjs`: 編集・比較・保存のUI。ユーザー入力はDOMのテキストとして表示
- `src/demo.mjs` / `fixtures/`: 架空のサンプル
- `tests/optimizer.test.mjs`: 別実装の全探索オラクル
- `scripts/`: ローカルサーバー、ベンチマーク、ブラウザ試験

素のES modulesを選び、配布・レビューに必要なファイルと実行時の依存を小さくした。規模が増えれば状態管理や部品化を見直す。バックエンド／認証／価格スクレイピングは問題を解くために不要なので追加しない。

## 最適化モデル

候補jの入数をs[j]、正の整数価格をc[j]、購入数を非負整数x[j]とする。購入必要数nに対して Σs[j]x[j] ≥ n を満たす。金額は Σc[j]x[j]、余りは Σs[j]x[j] − n。

最安は `(金額, 余り, パック数)`、余り最少は `(余り, 金額, パック数)` を辞書順に最小化する。同値なら入力候補の先頭から数を比較し、最初に異なる位置で数の多い解を選ぶ。この順序は再実行しても同じになる。ユーザーが候補順を変えた場合の同値解の変化は仕様。

### 有限の探索上限

最大入数をSとする。q ≥ n + S の購入では、含まれるどれか1パックを除いても必要数を満たす。価格は必ず正なので金額は減り、購入数量も減る。この解はどちらの目的でも最適でない。したがって調べる総購入数は0〜n+S−1で十分。

n=0ではどちらも購入なし。無償・負価格、クーポン、数量連動割引はこの証明とモデルに入らないので、入力として許可しない。

### DPと問い合わせ

q個をちょうど買う最安価格を小さいqから計算する。同じq・金額ならパック数と候補順で比較する。各遷移は1パックを足すため、より小さい数量の最適解を参照する。

すべてのqに対し、後ろ向きに「q以上で最安の総数量」と「最初の到達可能総数量」を計算する。これで最安と余り最少を定数時間で問い合わせられる（購入ベクトルの複製を除く）。同じ数量での同点解選択は両目的に共通。

人数0〜500の探索は最大人数で一度だけDPを構築し、各人数の必要量に問い合わせる。最安・余り最少の両ベクトルが同じ連続区間をまとめる。戻り値の`minPrice.surplus`と`minSurplus.surplus`は区間の開始人数`from`での値。区間内で余りは変わるため、UIの区間表には一定の「組み合わせと価格」のみ表示する。

### 計算量・数値

Q ≤ 10,999、K ≤ 6。数量・候補のループはO(QK)、同点でのベクトル比較・保存を含む最悪時間はO(QK²)。型付き配列の記憶量はO(QK)。人数区間は501回の問い合わせ。

必要量は最大10,000。価格最大100万円、1個パックのみの場合でも品目合計100億円、5品目500億円でNumberの安全な整数範囲内。価格はFloat64Arrayを使うが演算はこの範囲内の整数加算のみ。購入パック数は10,999以下でUint16Arrayに収まる。

最安で品目間の共通割引を考えないので、個別の最小値の和が全体最小値になる。余りは単位が異なるので単純合算しない。品目ごとの購入制限や店舗間の送料が入ると独立性が壊れ、別のモデルが必要。

## 性能上の判断

通常操作では参加人数だけが変わる。人数区間は品目条件のキャッシュを使い、展開されていない全区間表のDOMは作らない。キャッシュは上限26エントリ程度でクリアする。入力が無効なら出力を隠し、古い金額を誤って保存させない。

目標は通常操作200ms未満。実測はコアのみ。ブラウザのDOM・レイアウト試験は環境制限で未完了であり、低速端末の性能は不明。

## 先送りしたこと

- 真のPareto frontier：今回は二つの端点だけ。途中の「100円追加で余りを5個削減」などは列挙しない
- 手動で品目ごとに別方針を選ぶ機能：今回は全品目共通の方針切替
- 同時編集、クラウド保存、商品データの自動取得：需要検証前には追加しない
- 実店舗の在庫・送料・購入上限：現実的だがMVPの厳密な最適化条件を変える
