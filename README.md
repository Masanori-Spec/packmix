# PackMix

**人数と手持ち在庫から、備品パックの買い方を比べるブラウザツール。**

小規模イベントやワークショップで「32枚必要だが、12枚・20枚・50枚入りのどれを何個買う？」を考えるためのプロトタイプです。最安プランと余り最少プラン、人数変更で組み合わせが変わる境目を同じ画面で確認できます。

> 検証状態：50件のNodeテスト（独立全探索との1,000ケース比較を含む）と、17件のheadless Chromiumブラウザ試験に合格。[CI実行結果](https://github.com/Masanori-Spec/packmix/actions/runs/37096571750)はコミット`c3122c0b108e76d39e3aac673b58f2ef17f1990a`に対応します。デスクトップ幅・モバイル幅の画面も確認しました。実端末・他ブラウザ・包括的なアクセシビリティ監査は未実施です。

## 30秒でわかる例

名札カードを32枚用意する場合（在庫0枚、すべて架空の価格）：

| 候補 | 入数 | 税込価格 |
| --- | ---: | ---: |
| 小 | 12枚 | 400円 |
| 中 | 20枚 | 500円 |
| 大 | 50枚 | 800円 |

- **最安：50枚入り × 1 = 800円、余り18枚**
- **余り最少：12枚入り × 1 + 20枚入り × 1 = 900円、余り0枚**

最も単価が安いものを選ぶだけでは、余りを減らす選択や人数変更の影響はわかりません。PackMixは比較を残したまま、買い物リストまでつなぎます。

## 起動

Node.js 22以上が必要です。アプリ・コア試験に外部依存はありません。

```sh
npm start
# http://127.0.0.1:4173
```

ES modulesを使用するため、index.htmlのダブルクリックではなくHTTPサーバーで開いてください。公開用は静的ファイルのみで動きます。APIキー、アカウント、ビルドは不要です。

## 使い方

1. 参加人数、1人あたりの使用数、使える手持ち在庫を入力
2. 同じ品質・用途の備品について、パック入数と税込価格を登録
3. 「最安」「余り最少」を切り替え、買い物リストを比較
4. 人数の境目を確認し、リストをテキスト保存または印刷
5. 続きが必要なら計画をJSON保存。読み込むと現在の入力を置き換える

デモの価格と備品は架空です。実際の個人情報、取引情報、外部サービスへの接続は含まれていません。入力はメモリ内だけに保持され、ページを閉じると失われます。自動保存はありません。

## 範囲と制限

| 項目 | 上限／前提 |
| --- | --- |
| 参加人数 | 0〜500人、整数 |
| 品目 | 1〜5品目 |
| 各品目の候補 | 1〜6パック |
| 1人あたり使用数 | 1〜20、整数 |
| 手持ち在庫 | 0〜10,000、整数 |
| パック入数 | 1〜1,000、整数 |
| 1パック価格 | 税込1〜1,000,000円、整数 |
| JSON | UTF-8で64 KiB以下、version 1のみ |

購入必要数 = max(0, 人数 × 1人分 − 在庫)。余りは「新しく購入した数量 − 購入必要数」です。在庫の残りは別表示します。各品目は独立して最適化し、選んだ共通方針の金額を合算します。異なる単位の余りは合計しません。

**送料、クーポン、まとめ買い割引、店舗をまたぐ条件、販売在庫・購入上限、価格取得・注文は対象外**です。パックは無制限に買える前提で、入力された候補内だけの最適解です。食品・医療用品の調達用途は想定していません。

## 設計の要点

- 数量を状態とする動的計画法。貪欲法や近似ではなく、宣言範囲内で厳密に比較
- 正の価格により探索を `購入必要数 + 最大入数 − 1` で打ち切れることを利用
- 最安：金額 → 余り → パック数 → 上の候補を多く使う順
- 余り最少：余り → 金額 → パック数 → 同じ候補順
- 全人数の分岐はDP表を使い回し、同じ購入ベクトルの連続区間をまとめる
- インポートは厳密なキー／型／上限検証。HTML風の文字列もtextContentで扱い、実行しない
- CSP、外部リソースなし、入力の送信なし。検証失敗時は古い結果を隠す
- 境目の詳細表は開いたときだけ生成し、通常の人数変更のDOM負荷を抑える

証明・複雑度・数値精度は [設計メモ](docs/architecture.md)、安全性は [SECURITY.md](SECURITY.md) を参照してください。

## 既存製品との関係

混合パックの計算自体は既存です。新規性・特許性を主張しません。2026-10-03に公式ページ／リポジトリで以下を確認しました。

| 例 | 公開説明で確認した機能 | PackMixで試すワークフロー上の差分 |
| --- | --- | --- |
| [DataFirefly Quantity Calculator](https://www.datafirefly.com/en/documentation/dfsurfacecalculator/) | PrestaShopの商品画面で必要量を計算し、複数サイズの最安の組み合わせを提案 | イベントの人数と手持ち在庫から、最安と余り最少を比較し、人数の境目と買い物リストへつなぐ |
| [lushc/pack-calc-go](https://github.com/lushc/pack-calc-go) | 必要数量を満たすパック数を求めるGo実装。余剰・パック数の最小化 | 円価格を含む二つの目的、複数備品、ブラウザでの計画保存と人数変更の検討 |
| [tooloo 商品単価計算](https://tooloo.net/tools/unit-price-calculator/) | 容量・数量と価格から単価を比較 | 単価の比較から、必要数を満たす混合パックの数量決定へ |

これは公開説明に基づく限定的な比較です。各製品の全機能や市場を網羅した調査ではありません。**利用者需要・継続利用・支払意思は未検証**です。差分の有用性は、実際の主催者に作業をしてもらう検証が必要です。

## 試験と実測

```sh
npm run check
npm run benchmark
node --test --experimental-test-coverage tests/*.test.mjs
```

- 50テストに合格、1,000件の固定シード小規模問題を独立した全組み合わせ列挙と照合
- 在庫充足、価格／余り／パック数の同点、候補6個、人数0・500、最大合計500億円を確認
- 不正値、欠落キー、余分なキー、prototype pollution、深すぎるJSON、UTF-8容量制限を確認
- optimizer.mjsの行／関数カバレッジ100%、分岐98.99%。UIのカバレッジではありません

2026-10-03、Node v24.19.0 / Linux x64 / AMD EPYC 9V74のクラウド環境、5回ウォームアップ後50回。現在人数の計算＋各品目の0〜500人全分岐を含み、DOM・描画・I/Oを除きます。

| ケース | 中央値 | p95 | 最大 |
| --- | ---: | ---: | ---: |
| デモ（2品目、32人） | 0.98ms | 1.41ms | 4.51ms |
| 宣言上限（5品目×6候補、500人×20、最大入数1,000） | 14.16ms | 14.84ms | 16.15ms |

200msは通常操作の目標です。上記はコア計算の測定であり、端末・ブラウザ全体の速度保証ではありません。生データは [benchmark.json](docs/benchmark.json)、試験出力は [test-results.txt](docs/test-results.txt) にあります。

### ブラウザ試験（CIで17件合格）

```sh
npm install --no-save --ignore-scripts playwright@1.62.1
npx playwright install chromium
npm run test:browser
```

通常のLinux CIでは `npx playwright install --with-deps chromium` を使用します。`CHROMIUM_PATH`で既存の実行ファイルを指定できます。公開CIは`.github/workflows/quality.yml`で同じ手順を行います。

2026-10-03 04:27:47 UTCに、GitHub ActionsのLinuxランナー上で **headless Chromium 154.0.8037.0** による17件の試験が合格しました。デモ計算、方針切替、無効値からの復帰、不正な行の削除、JSON攻撃、読込中のキャンセル、保存内容、人数境目、長い文字列・最大金額、外部通信を検査しています。ページエラーは0件、観測されたリクエストはローカルの静的リソースのみでした。

- 設定したビューポート：1440×1100、390×844、320×740 CSS px
- モバイル幅は同じheadless Chromiumのウィンドウサイズ変更。iPhoneなどの実端末、Safari、タッチ操作の検証ではありません
- デモの人数変更を30回測定：中央値2.7ms、p95 3.1ms、最大3.3ms
- 測定範囲：イベント発火 → 同期計算 → DOM更新 → 強制レイアウト。**paint（画面の描画）、人の操作時間、低速端末での動作を含みません**
- JSONインポート／エクスポートとテキスト保存を検査。印刷ダイアログの動作、包括的なキーボード操作・スクリーンリーダー対応は未検証

生データ：[browser-results.json](docs/browser-results.json)。架空デモの実際のCIスクリーンショット：[デスクトップ](docs/screenshots/desktop.png)／[390px幅](docs/screenshots/mobile.png)。両画像を目視確認し、確認した状態で意図しない横方向のはみ出しは見られませんでした。すべての入力・表示状態の視覚保証ではありません。
